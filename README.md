# CircuitPilot

CircuitPilot supports deterministic graph-to-Simulink generation, a natural-language planner, a local FastAPI service and React frontend, and a bounded verification-driven repair loop for classical control systems. Power electronics are not supported.

## Layout

- `circuitpilot/ir.py`: Pydantic component graph and deterministic validation.
- `circuitpilot/generator.py`: optional MATLAB Engine bridge; core IR remains importable without MATLAB.
- `circuitpilot/planner.py`: provider-specific structured-output adapters, deterministic mock, and graph-validation boundary.
- `circuitpilot/matlab/circuitpilot_generate_and_simulate.m`: controlled R2024b-compatible model builder and simulation/output extraction.
- `examples/closed_loop_pid.json`: first configurable closed-loop PID specification; the generator accepts arbitrary supported graphs.
- `tests/`: environment-independent validation tests.
- `frontend/`: React + Vite UI connected to the local baseline-run API; demo values are visibly labeled before a run.

## Frontend preview

See [frontend/README.md](frontend/README.md) for setup. Install the API extra with `python -m pip install -e ".[api,llm]"`, then run `python -m uvicorn circuitpilot.api:app --host 127.0.0.1 --port 8000 --workers 1` from the repository root. In another PowerShell window, run `cd frontend; npm install; npm run dev`. The frontend sends the prompt, duration, and an opt-in repair boolean; provider credentials remain in the backend environment. API runs use one MATLAB worker and isolated `artifacts/api_runs/<run-id>` directories. Automatic repair is disabled by default.

Completed run results include a **Generated Simulink Model** panel. Download resolves the selected/best attempt's `.slx` from that run's saved report and repair history. The optional **Open in MATLAB** action is restricted to loopback clients and launches only a MATLAB executable; set `CIRCUITPILOT_MATLAB_EXECUTABLE` to the full local `matlab.exe` path, or make `matlab` available on `PATH`. This is a local-development feature: the frontend and API must run on the same Windows machine. The launch request returns after asking Windows to start MATLAB; it does not confirm that MATLAB finished opening the model. Original repair-attempt models can be downloaded separately from repair history.

### API run persistence and execution limits

The API stores run status and stage in `artifacts/api_runs/run_registry.sqlite3` (or beside the configured `CIRCUITPILOT_API_OUTPUT` directory). Per-run `verification_report.json` and `verification_report.md` remain the detailed report source of truth. On API startup, persisted `queued` or `running` entries are reconciled: runs with a completed report and durable simulation result remain completed; other active entries become `interrupted`, and their report is checkpointed accordingly. Run IDs are generated by CircuitPilot and API artifact routes accept only those IDs, never caller-provided filesystem paths.

The API keeps a single MATLAB worker and caps accepted active/queued work with `CIRCUITPILOT_API_QUEUE_CAPACITY` (default `2`, which allows one running and one queued run). The frontend sends an `Idempotency-Key` with each user-initiated submission; the SQLite registry stores its hash and returns the existing run for a repeated key, including after an API restart. The browser also blocks overlapping submissions in the same page. Configure the total queue-plus-execution deadline with `CIRCUITPILOT_API_EXECUTION_TIMEOUT_SECONDS` (default `1800`, allowed range `1` to `86400`):

```powershell
$env:CIRCUITPILOT_API_OUTPUT = "artifacts/api_runs"
$env:CIRCUITPILOT_API_QUEUE_CAPACITY = "2"
$env:CIRCUITPILOT_API_EXECUTION_TIMEOUT_SECONDS = "1800"
$env:CIRCUITPILOT_API_MAX_REPAIR_ATTEMPTS = "2"
python -m uvicorn circuitpilot.api:app --host 127.0.0.1 --port 8000 --workers 1
```

The API accepts `"auto_repair": true` in `POST /api/runs` to opt a single run into the existing bounded repair loop. Omitting the field (or sending `false`) preserves the baseline-only workflow. The server caps configured repair proposals at 5 (`CIRCUITPILOT_API_MAX_REPAIR_ATTEMPTS`, default `2`); the browser cannot raise this limit. Reusing an idempotency key returns the originally accepted run and its original repair choice.

```json
{"prompt":"Build a unit-step PID loop and verify overshoot <= 5%","simulation_duration_seconds":10,"auto_repair":true}
```

Repair tuning is limited to `P`, `I`, `D`, and `N` on an existing `PID Controller`, plus simulation duration up to 86400 seconds. Each original/repaired attempt has a distinct directory under that API run's `repairs/<run-id>/`; the original model and measurements are retained. The status endpoint exposes the repair opt-in and configured attempt limit; the report endpoint exposes the attempt history, individual verification results, and selected best attempt. Inconclusive metrics do not trigger a repair. A rejected proposal or failed execution stops the workflow; a passing simulation is not implied by API request completion. The worker/timeout limitations above also apply during repair: the API cannot forcibly cancel an in-flight MATLAB Engine operation, and a timed-out worker may remain occupied.

A deadline produces a persisted `failed` run with a sanitized `TIMEOUT` diagnostic. Python cannot safely forcibly stop a running worker thread or guarantee cancellation of an in-flight MATLAB Engine call. If a call exceeds the deadline, the API marks the run terminal for clients but keeps the single worker occupied until the call returns; subsequent work remains serialized and the accepted queue stays bounded. A process restart can interrupt the engine process itself, so do not use server restarts as a cancellation mechanism. Forced process termination or a machine crash can prevent a last report write; startup recovery marks any remaining active registry entry interrupted. Run the API with one Uvicorn worker, as above, so separate web processes cannot create overlapping MATLAB workers.

## Run

Run the full offline test suite:

```powershell
python -m unittest discover -s tests -v
```

The JSON-to-Simulink path remains available:

```powershell
python -m circuitpilot.cli examples/closed_loop_pid.json --output artifacts
```

The command writes `artifacts/ClosedLoopPID.slx` and prints the sampled output. The selected output is tapped into an internal To Workspace block; Scope remains part of the editable model.

For natural-language planning, install the optional provider SDKs:

```powershell
python -m pip install -e ".[llm]"
```

CircuitPilot automatically reads `.env` from the project root before resolving the provider, model, or API key. Existing process environment variables take precedence. Copy `.env.example` to `.env` and replace the placeholder for the provider you use; `.env` is ignored by Git.

Choose OpenAI, xAI Grok, or Google Gemini. Enter the API key at a hidden prompt to avoid putting it in shell history. The value is held only in the current PowerShell process environment.

OpenAI:

```powershell
$env:OPENAI_API_KEY = [System.Net.NetworkCredential]::new("", (Read-Host "OpenAI API key" -AsSecureString)).Password
$env:CIRCUITPILOT_PROVIDER = "openai"
$env:CIRCUITPILOT_MODEL = "gpt-4o-mini"
python -m circuitpilot.cli --prompt "Create a unit-step closed-loop PID for plant 1/(s^2 + 2s + 1), with P=2, I=1, D=0, simulate for 10 seconds" --output artifacts --graph-output artifacts\planned_pid.json
```

xAI Grok:

```powershell
$env:XAI_API_KEY = [System.Net.NetworkCredential]::new("", (Read-Host "xAI API key" -AsSecureString)).Password
$env:CIRCUITPILOT_PROVIDER = "grok"
$env:CIRCUITPILOT_MODEL = "grok-4.7"
python -m circuitpilot.cli --prompt "Create a unit-step closed-loop PID for plant 1/(s^2 + 2s + 1), with P=2, I=1, D=0, simulate for 10 seconds" --output artifacts --graph-output artifacts\planned_pid.json
```

Google Gemini:

```powershell
$env:GEMINI_API_KEY = [System.Net.NetworkCredential]::new("", (Read-Host "Gemini API key" -AsSecureString)).Password
$env:CIRCUITPILOT_PROVIDER = "gemini"
$env:CIRCUITPILOT_MODEL = "gemini-3.8-flash"
python -m circuitpilot.cli --provider gemini --model gemini-3.8-flash --prompt "Create a unit-step closed-loop PID for plant 1/(s^2 + 2s + 1), with P=2, I=1, D=0, simulate for 10 seconds" --output artifacts --graph-output artifacts\planned_pid.json
```

The same settings can be passed with `--provider openai|grok|gemini` and `--model MODEL`; command-line options override environment variables. Defaults are `gpt-4o-mini` for OpenAI, `grok-4.7` for Grok, and `gemini-3.8-flash` for Gemini; `CIRCUITPILOT_MODEL` overrides the selected provider default. The Gemini adapter uses Google's `google-genai` SDK and Interactions API, with a JSON Schema derived from the Pydantic response envelope. It explicitly targets Interactions API `v1beta`, which was verified against the configured project; GenerateContent diagnostics use the SDK default endpoint. Google documents the structured `response_format` schema and its REST route in the [structured output guide](https://ai.google.dev/gemini-api/docs/structured-output). The [model catalog](https://ai.google.dev/gemini-api/docs/models) lists the current model. OpenAI and Grok continue using the Responses API; the Grok adapter uses `https://api.x.ai/v1` and `XAI_API_KEY`. See [xAI Structured Outputs](https://docs.x.ai/developers/model-capabilities/text/structured-outputs) and [xAI API endpoints](https://docs.x.ai/developers/rest-api-reference/inference).

To diagnose Gemini connectivity and schema issues without generating a model, run a Gemini command with `--diagnose-gemini`. CircuitPilot tests plain Interactions, minimal structured Interactions, then the CircuitPilot envelope schema; if both Interactions probes fail, it also tests plain `generate_content`. The report includes the configured key variable name and endpoint, but never the key or request headers.

The prompt route asks the model for a structured response envelope, validates the embedded graph against the Pydantic schema and graph rules, saves that graph JSON, then invokes the same MATLAB generator as the JSON route. Ambiguous requests and unsupported component families stop before MATLAB is started.

Every generated simulation result now includes a verification report. It checks simulation status and finite, aligned samples, and reports final-value tracking error, peak overshoot, and settling time for a single-step response. Performance limits are optional and belong in the model specification's `verification` object, for example `{"max_tracking_error": 0.01, "max_overshoot_percent": 10, "max_settling_time": 5, "settling_band_percent": 2}`. Without a requested limit, the metric is included but its criterion status is `inconclusive`; the settling-time measurement uses a 2% step-amplitude band by default and states that convention in the report.

Each CLI run also writes a persistent human-readable run report and its JSON data. For a normal JSON or prompt run, find both files at `artifacts\run_reports\<run-id>\verification_report.md` and `verification_report.json` (replace `artifacts` with the selected `--output` directory). The report is created before planning or specification loading, then updated at generation, simulation, and verification checkpoints. Planning, validation, MATLAB startup, and simulation errors are recorded with sanitized error categories; report files never include provider credentials, request headers, prompt content, raw response bodies, or raw exception messages. `PASS`, `FAIL`, and `INCONCLUSIVE` retain the verifier's existing semantics; infrastructure and planning errors are reported separately as `ERROR`.

## Bounded automatic repair

Pass `--auto-repair` to run the original model and, only when one or more verification checks fail, ask the selected structured-output planner for a targeted repair. The default limit is two repair proposals; `--max-repair-attempts` accepts an integer from 0 through 5. The API uses the same server-side maximum. Inconclusive metrics do not trigger repairs.

JSON specification example:

```powershell
python -m circuitpilot.cli examples/closed_loop_pid.json --output artifacts --auto-repair --max-repair-attempts 2
```

For a repeatable PID repair run with explicit acceptance criteria, use the separate demo specification and output root below. The demo sets maximum tracking error to `0.01`, maximum overshoot to `5%`, and maximum settling time to `5` seconds; repair artifacts are isolated under `artifacts\pid_repair_demo\repairs\...`.

```powershell
python -m circuitpilot.cli examples/closed_loop_pid_repair_demo.json --output artifacts\pid_repair_demo --auto-repair --max-repair-attempts 2
```

Natural-language example (provider/model credentials configured as above):

```powershell
python -m circuitpilot.cli --provider gemini --model gemini-3.8-flash --prompt "Create a unit-step closed-loop PID for plant 1/(s^2 + 2s + 1), with P=2, I=1, D=0, simulate for 10 seconds" --output artifacts --graph-output artifacts\planned_pid.json --auto-repair --max-repair-attempts 2
```

Each CLI repair run is stored beneath `artifacts/repairs/<unique-run-id>/`, with separate `attempt_00_original`, `attempt_01_repair`, and subsequent directories. API repair runs use the same layout inside their unique API run directory. Each repair folder contains `repair_report.json` and a `verification_report.md` updated at checkpoints. Each simulation attempt stores its specification, raw simulation result, and verification report; repair attempts also store the structured proposal. Reports record diagnoses, measured checks, changes, rejected proposals, errors, and the best verification result seen. The UI shows each attempt and the final repair outcome separately from simulation execution status. Models are never copied over or promoted automatically, so inspect the reported attempt path before choosing a model. Repairs can tune only `P`, `I`, `D`, or `N` on an existing PID Controller and change the simulation duration (maximum 86400 seconds). They cannot change component types, graph topology, output selection, or user acceptance criteria. Every patch is validated with the existing Pydantic and graph checks before generation. A MATLAB/generator exception stops the loop and is recorded; invalid proposals are rejected without another simulation. This bounded feature is not an engineering guarantee, and an LLM-proposed parameter change still requires review.

Planner requests retry transient HTTP `429` and `5xx` responses, including `503`, with exponential backoff and jitter. A provider's `Retry-After` value is honored as a minimum wait, up to the 30-second per-wait cap. The default is two retries after the initial request; configure a limit from 0 to 5 with:

```powershell
$env:CIRCUITPILOT_LLM_MAX_RETRIES = "2"
```

Each provider request has a 60-second timeout by default. Configure it from 1 to 300 seconds with `$env:CIRCUITPILOT_LLM_TIMEOUT_SECONDS`; CircuitPilot retries are the sole retry layer and are bounded by the configured retry count. Retry delays, including `Retry-After`, are capped at 30 seconds per wait. For `google-genai 2.31.0`, CircuitPilot explicitly sets the constructed Gemini client's internal `retry_options.attempts` to zero after initialization. This works around the SDK's normalization of the documented `attempts=0` setting to `1`, which its Interactions adapter interprets as one additional retry. A guard fails clearly if a Google SDK client no longer exposes the expected option.

If Ctrl+C is received during a handled CLI stage, CircuitPilot checkpoints the run as `ERROR` / `INTERRUPTED` and exits with status 130. Forced process termination or machine crashes cannot run that handler.

Authentication, invalid-request, schema-validation, and other permanent client errors are not retried. If repair planning ultimately fails, its report entry retains the original diagnosis and records the retry count, safe final provider error, and whether the final failure was transient. A failed repair-planning request ends the loop without rerunning MATLAB.

The repair JSON and Markdown reports are checkpointed before provider and simulation calls and updated after each completed attempt. A user interrupt is recorded as `interrupted`; provider timeouts, HTTP errors, and unexpected planner exceptions have distinct failure types. A forced process termination or machine shutdown cannot execute cleanup code, so the last checkpoint may remain `status: running` with an attempt phase such as `planning` or `simulating`; that checkpoint preserves the diagnosis and tells you where execution stopped. Forced termination and machine crashes cannot be reported as handled errors.

The planner is not a safety-certified engineering design system. Component types and parameter values are validated, but the current phase does not prove that an arbitrary model meets performance, stability, units, or physical-design requirements. Model-generated parameters and assumptions should be reviewed before use.
